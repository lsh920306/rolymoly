# 실시간 경매 지연 개선 검증

작성일: 2026-09-10 KST. 전체 회귀 790개, 실제 PostgreSQL 정합성 검증, TCP 및 브라우저의 정상·마감 직전·느린 통신망·재접속 전후 비교를 완료했습니다. 지연은 줄었지만 한 PC의 80개 브라우저 문서 시험에서 200/300/500ms 목표를 모두 충족하지 못했습니다. 국내 실제 기기 80대의 운영 환경 목표 충족 여부는 아직 검증하지 않았습니다.

## 목표와 판정 방법

사용자의 최종 조건은 평소 60명 이하, 최대 80명입니다. 아래 부하 시험은 팀장 4명과 관전자 76명을 합한 최대 80명으로 유지했습니다. 60명의 지연을 80명 수치에 비례해 추정하지 않습니다. 다음 기준은 실제 국내 접속 환경에서 검증해야 합니다. 한 PC의 80개 문서나 TCP 연결에서 통과하더라도 운영 환경 목표를 충족했다고 표현하지 않습니다.

이 숫자는 사용자가 정한 Rolymoly의 목표입니다. [RAIL](https://web.dev/articles/rail)의 100ms 반응 지침과 [INP](https://web.dev/articles/inp)의 화면 반응 지표는 참고할 수 있지만, DB 저장 확정과 상대방 전달 시간은 별도로 측정해야 합니다. 평균 외에 느린 요청의 분포를 보는 이유는 [Google SRE의 지연 측정 설명](https://sre.google/sre-book/monitoring-distributed-systems/)과도 일치합니다.

| 지표 | 목표 | 반드시 함께 기록할 값 |
|---|---:|---|
| 입찰 클릭 후 시각적 반응 | 100ms 이내 | 측정 대상 DOM/화면 변화, 평균, p95, p99, 최대 |
| 입찰 클릭 → 확정 ACK | p95 ≤ 200ms, p99 ≤ 500ms | 평균, 전체 시도 수, 승인/거절별 수치, 1초 초과 건수, 최대 |
| 입찰 클릭 → 다른 참가자 DOM 반영 | p95 ≤ 300ms, p99 ≤ 500ms | 평균, 승인 입찰 수, 관측/예상 참가자 쌍 수, 1초 초과 건수, 최대 |
| 시간 초과·미확정·반영 누락 | 모든 시도를 분모에 포함 | 각각의 건수와 비율, 오류 종류, 재접속 후 복구 결과 |

정상 입찰과 마감 직전의 팀장 동시 입찰을 구분합니다. 최초 80명 접속, 재접속, 느린 통신망 조건도 별도로 기록합니다. 시간 초과나 DOM 누락을 제거해 성공한 표본만으로 통과를 판정하지 않습니다. 완료된 요청의 지연 분포를 제시할 때도 전체 시도 수와 미완료 수를 같은 표에 표시합니다.

분위수는 정렬된 표본의 `ceil(p × n)`번째 값인 nearest-rank 방식으로 계산합니다. 평균과 p95를 반드시 함께 제시하고 p99, 최대, 1초 초과 건수를 추가합니다. 같은 승인 입찰이 79개 화면으로 전파된 관측은 서로 관련된 표본입니다. 참가자별 전체 관측 분포와 입찰별 79명 중 가장 늦은 반영 시간을 구분하며, 79배의 독립 입찰 시험으로 세지 않습니다.

## 80개 브라우저 문서: 정상 입찰 비교

**지연과 긴 지연 건수는 감소했지만, 고정된 가시 화면 조건에서 목표를 모두 충족하지 못했습니다.** 한 PC의 브라우저에서 80개 독립 origin·합성 세션을 사용했습니다. 팀장 4명과 관전자 4명은 큰 프레임으로 고정 배치하고, 나머지 72명은 작은 프레임에서 실제 제품 DOM을 실행했습니다. 검수 문서에만 CSS zoom 0.7을 적용했으며 제품 JS·CSS는 변경 전후 원본 그대로입니다. 실제 80대 기기, 원격 앱·DB·TLS의 성능을 입증하는 시험은 아닙니다.

20명의 합성 선수와 4개 팀으로 만든 격리 SQLite 경매를 사용하며 실제 경매 시각과 마감 워커를 실행합니다. 운영 회원 데이터나 Riot HTTP 호출은 사용하지 않습니다. 각 모드에서 정상 승인 입찰 100건, 다른 79명에 대한 DOM 관측 7,900쌍을 기록했습니다. 100개 클릭·전송 UUID·승인 ACK·DB 저장 행이 일치했습니다. 미시도·미확정·추가 전송·시간 초과·오류·DOM 누락·가격 역행은 모두 0입니다. 첫 80명 준비는 변경 전 4,625ms, 변경 후 4,461ms였으며 정상 입찰 분포와 구분합니다.

### 측정 조건과 초기 시도

한 PC에서 80개 문서의 100ms DOM/시계 갱신과 측정 작업이 함께 실행됩니다. 가시성 확인은 요소 위치·스타일 계산을 유발할 수 있고, 각 문서의 상태 메시지 처리 비용도 들어갑니다. 이 비용은 양쪽에 같게 적용했지만 실제 80대 기기의 분산된 렌더링과는 다릅니다. CPU 포화를 직접 계측하지 않았으므로 지연의 전부를 브라우저 탓이라고 단정하지 않습니다.

브라우저의 창·탭 스케줄링도 별도 변수입니다. [Chromium의 Windows 창 가림 처리 설명](https://blog.chromium.org/2021/12/chrome-windows-performance-improvements-native-window-occlusion.html)은 다른 창에 완전히 가려진 Chrome의 우선순위를 낮추는 동작을 설명합니다. 이번 기록은 DOM 내부 가시성·문서 표시 상태를 확인했지만 운영체제 합성기의 실제 표시나 절전 정책 적용 여부를 계측하지 않았습니다. 해당 정책이 이번 긴 rAF 지연의 원인이었다고 확정하지 않습니다.

[앞선 DOM 전용 비교](../test-artifacts/push-20260910/browser-comparison-root-normal-2.md)는 ACK p95 445.4→196.4ms, 다른 DOM p95 759.5→191.2ms였으나 결과표 성장에 따라 프레임 노출이 달라지고 버튼·메시지가 잘려 가시성이 보장되지 않았습니다. 이 결과의 DOM 정합성은 유지하며, 실제 시각 반응 목표 통과의 근거로 사용하지 않습니다. 당시 [하네스 v1](../test-artifacts/push-20260910/browser-benchmark-v1.py)을 SHA가 일치하는 상태로 보존했습니다.

[첫 초기 접속 실패](../test-artifacts/push-20260910/browser-attempt-root-normal-1.json)는 8.5시간 작업 중단 후 합성 관전자 76개의 1시간 세션이 만료된 경우로, 입찰 시도는 0건이었습니다. 새 fixture의 서로 다른 80개 계정을 사전 인증하는 검사를 추가했습니다. 이후 측정 전후 소스·하네스 해시를 확인합니다.

## 보충 조건: 브라우저 8개 + TCP 관전자 72명

총 80개의 서로 다른 계정 접속을 유지하면서 브라우저 문서를 8개로 줄인 별도 비교입니다. 나머지 72명은 별도 Python 프로세스에서 실제 TCP 연결로 상태를 수신합니다. 이 조건은 위의 80문서 시험을 대체하지 않으며, 72명의 화면 표시 시간을 측정한 것도 아닙니다. 정상 승인 입찰을 각 100건 실행했습니다.

전후 각각 클릭 100건·UUID 100개·승인 100건·DB 원장이 일치했고 미확정·추가 전송·시간 초과·DOM 누락·가격 역행은 0건입니다. 다른 브라우저 700/700쌍과 TCP 7,200/7,200쌍을 검산했고, 종료 전 전체 80명의 상태가 최신 DB 가격·입찰 번호·마감 시각과 일치했습니다. TCP 상태 확인은 250ms 간격이고 매 입찰 후 8개 DOM·72개 TCP의 수렴을 기다리므로, 이 절차가 다음 입찰 간격에 영향을 줍니다. 준비 시간은 이미 TCP 72명이 접속한 후 브라우저 8개를 여는 과정이므로 80명 동시 cold 접속으로 해석하지 않습니다.

## 바뀐 구조

입찰은 기존 Python POST 경로와 DB 트랜잭션을 유지합니다. 권한, 현재 선수, 팀 예산·정원, UUID 재시도, 서버 시각의 마감 판정은 저장 단계에서 확인합니다. 관전자에게 상태를 보내는 작업은 입찰 확정 응답과 독립적으로 처리합니다. 화면 캐시를 입찰 판정의 근거로 사용하지 않습니다.

경매별 공통 상태는 [auction_push.py](../roly/auction_push.py)의 서버 내 공유 작업이 관리합니다. 접속자마다 프로필과 긴 기록을 다시 읽던 경로를 줄이고, [auction_state.py](../roly/auction_state.py)에서 연결된 세션을 한 쿼리로 검증합니다. 최초 접속과 상세 정보 변경에는 전체 상태를 만들고, 일반 입찰에는 헤더·현재 lot·최근 입찰/이벤트 각 30건을 읽어 기존 상세 정보와 합칩니다. 변경이 없으면 버전·전체 세션 인증·DB 시각만 읽습니다.

PostgreSQL 스키마 v8은 `_auction_versions`와 변경 감지 트리거를 추가합니다. 각 경매의 버전과 공통 인증/프로필 버전이 실제 데이터 변경 트랜잭션 안에서 증가합니다. 상세 버전은 팀·선수·프로필·경매 차례 등의 변경을 구분합니다. 롤백되면 버전 증가와 통지도 취소됩니다. 한 트랜잭션의 여러 쓰기가 버전을 여러 번 증가시킬 수 있으므로 버전 사이의 숫자 차이를 곧바로 데이터 누락으로 해석하지 않습니다.

입찰 API 외에도 별도 마감 워커, 관리자 정정, 회원·프로필 변경, 로그아웃·계정 비활성화를 트리거가 포착합니다. PostgreSQL의 커밋 후 NOTIFY는 조회를 깨우는 신호이며, 통지 자체를 영구 기록이나 권한 근거로 사용하지 않습니다. [auction_notifications.py](../roly/auction_notifications.py)는 앱의 트랜잭션 연결 풀과 분리된 전용 LISTEN 연결을 사용합니다. 연결이 다시 열리면 최신 버전을 조회하고, 통지를 놓쳐도 기본 1초 버전 확인으로 복구합니다. 배치 환경에서는 해당 DB 연결 경로가 지속적인 세션과 LISTEN을 지원해야 합니다.

WebSocket의 각 갱신은 현재의 작은 상태를 완결된 형태로 전달합니다. 느린 수신자의 큐는 최신 상태 하나로 제한하고 아직 전달되지 않은 상세 정보는 유지합니다. 클라이언트는 서버 실행 세대, 문맥, 경매 번호와 버전 순서를 검증하며, 오래된 상태를 버리고 재접속 시 스냅샷으로 복구합니다. 시계와 상태의 신선도가 확인되지 않으면 입찰을 계속 허용하지 않습니다. 클라이언트의 시계 계산은 서버 시각과 monotonic 경과 시간을 사용합니다.

세션 만료는 기존 Core의 UTC 기준을 유지하며, SQL 조회 전뿐 아니라 풀 대기와 상태 변환을 마친 조회 반환 직전에도 확인합니다. 경매 마감의 PostgreSQL 시각과 인증용 시각을 임의로 바꾸지 않았습니다. 스키마 전체의 기존 쓰기 잠금과 앱·DB 배치 지역은 이번 변경으로 제거하거나 이전하지 않았습니다.

| 관리자 낙찰 정정 | 1 | 290.221 | 290.221 |

`n=1`의 표본 p95는 그 한 관측값 자체이며 지속적인 p95를 입증하지 않습니다. 위 동작은 서로 다른 작업이므로 합산해 하나의 입찰 지연 분포로 제시하지 않습니다.

단일 정상 승인 48.435ms에서 `writer_begin`은 13.336ms, 쓰기 pipeline은 22.009ms, COMMIT은 10.035ms였습니다. `writer_begin`에는 쓰기 시작·잠금 대기·인증/검증 조회가 함께 들어가므로 13.336ms를 순수 잠금 대기로 부르지 않습니다. 작업별 풀 checkout, rollback 등은 원본 `samples[].stages`에 있으며, 풀 반환·검사 백그라운드 통계는 요청 지연과 분리했습니다.

## 80개 TCP 연결 비교: 완료

보관된 v7 제품 소스와 변경 후 v8 제품을 각각 별도 프로세스로 실행합니다. 같은 PC의 TCP 연결 80개, 서로 다른 합성 계정·세션 80개, 팀장 4명·관전자 76명을 사용합니다. 변경 전은 접속자마다 250ms 목표 간격과 동시 미완료 조회 1개를 적용하고, 변경 후는 WebSocket과 경매별 공유 조회를 사용합니다.

아래 변경 전 수치는 [TCP 변경 전 원본](../test-artifacts/push-20260910/tcp-before-60s.json)과 [요청별 원본](../test-artifacts/push-20260910/tcp-before-60s.samples.jsonl)을 [비교 실행기](../test-artifacts/push-20260910/tcp-compare.py)로 집계한 것입니다. 60라운드 모두 1승인·3거절, 총 240건과 승인 60건, 다른 79명에 대한 관측 4,740쌍이며 누락은 0쌍입니다.

| TCP 지표 | 변경 전 평균 / p95 / p99 / 최대 (ms) | 최종 변경 후 평균 / p95 / p99 / 최대 (ms) |

양쪽 각각 60회 경쟁·240개 ACK·60개 승인 저장이 일치했습니다. 시간 초과·미확정·가격 역행·다른 참가자 수신 누락·1초 초과는 모두 0건입니다. 전체 ACK p95는 55.941→56.578ms로 소폭 증가했으므로 모든 지표가 개선됐다고 표현하지 않습니다. 전체 ACK p99와 최대, 승인 ACK, 관전자 전달 지연은 감소했습니다.

약 60초 동안 변경 전 전체 조회는 16,212회, 변경 후 공유 조회는 64회였습니다. 변경 후 전체 상세 상태는 이미 준비된 1개를 재사용했고 hot 상태를 60회 갱신했습니다. 측정 구간의 JSON/HTTP 응답 바이트는 약 491.6MB→20.4MB로 줄었습니다. TCP·WebSocket 프레임, TLS 및 모든 네트워크 오버헤드를 포함한 전송량은 아닙니다.

이 시험은 가상 경매 시각을 고정하고 자동 낙찰 워커를 끈 전송 부하 비교입니다. 마감 규칙 검증과 분리합니다. 실제 브라우저 클릭, DOM·paint, TLS, 원격 PostgreSQL, Cloud 또는 지역 간 통신을 포함하지 않습니다. 중간 수정본의 `tcp-after-60s.json`과 구분해 최종 동결 소스의 `tcp-after-final-60s.json`을 사용했습니다. ## 검증 소스와 남은 확인

최종 동결 소스의 전체 회귀는 **790개·542.358초 통과**했습니다. 고유 테스트 790개에 대해 누락·중복·미완료·실패가 없었고, 검사 전후 제품·테스트 등 167개 파일의 해시가 일치했습니다. 기존 검증 실행기를 네 개의 독립 프로세스로 나눠 실행했으며 비공개 운영 파일·외부 네트워크·실제 PostgreSQL 접근 시도는 모두 0회였습니다. [전체 회귀 원본](../test-artifacts/push-full-20260910-verification.json)

실제 PG 최종 기록은 실행 전후 소스 해시가 같음을 확인했습니다. 이후 WebSocket 구독의 await 이후 종료 상태 확인이 수정되었으므로, 이 PG 기록을 현재 전체 제품 소스가 다시 검증됐다는 증거로 확대하지 않습니다. PG 검증 대상인 상태 조회·트리거·DB 어댑터·입찰 도메인은 이후 바뀌지 않았습니다. 이후 변경된 전송 코드를 포함한 최신 소스 전체는 790개 회귀, 최종 TCP 및 브라우저 기록의 해시로 대조합니다.

프로세스 종료·늦은 응답·느린 수신자 큐·권한 변경은 최신 소스의 회귀 검증에 포함했습니다. 로컬 브라우저의 정상·마감 직전 경쟁·느린 통신망·재접속은 위의 전후 원본에 평균·p95·p99·최대·1초 초과·전체 분모와 오류를 남겼습니다. DOM 복구에 성공한 경우에도 해당 상태의 가시적 rAF 증거가 없는 표본을 화면 표시 성공으로 바꾸지 않았습니다.

남은 운영 검증은 국내 기기에서 평소 60명 이하와 최대 80명이 실제 배포 서버와 DB를 함께 거치는 같은 시나리오의 측정입니다. 서버 지역 이전이나 외부 배포는 실행하지 않았습니다. 현재 수정 방향의 상태 공유·중복 방지·변경 복구는 검증됐지만, 마감 직전에도 지연 목표를 안정적으로 지켰다고 결론 내릴 수는 없습니다.

첨부한 무료 운영·브라우저 직접 RPC 제안은 [별도 검토서](AUCTION_HOSTING_REVIEW.md)에 공식 제한과 현재 코드의 차이를 정리했습니다. 현재 자체 WebSocket에는 Supabase Realtime의 초당 메시지 제한이 적용되지 않으며, 직접 RPC와 Supabase Realtime 후보를 이번 제품에 추가하지 않았습니다.
