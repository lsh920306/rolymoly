# 입찰 저장·COMMIT 통합 검증 — 2026-09-10

입찰 전용 최종 저장 API를 구현하고 실제 Supabase PostgreSQL에서 변경 전후를 비교했다. 정상 입찰의 DB 동기화 구간은 모든 표본에서 3회에서 2회로 줄었고, 평균은 25.57%, p95는 25.48% 감소했다. 검증한 조건에서는 원자성·중복 방지·마감 연장을 유지했다. 이번 변경의 운영 사이트 배포와 DB 리전 이전은 실행하지 않았다.

## 정상 입찰 측정

동일 PC에서 기존 원격 Supabase DB에 접속해 별도의 신규 QA 스키마를 전후 각각 생성했다. 합성 회원 20명·팀장 4명, 준비 입찰 10건 이후 정상 증가 입찰 100건씩을 직렬 측정했다. 측정 범위는 Python `place_bid()` 호출부터 반환까지이며 연결 풀 대기와 DB 처리를 포함한다. 비교 중 회귀 테스트는 병렬 실행하지 않았다.

| 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| 요청 / 승인 / 실패 / 누락 | 100 / 100 / 0 / 0 | 100 / 100 / 0 / 0 |
| 평균 | 39.177ms | 29.160ms |
| p50 | 39.582ms | 28.930ms |
| p95 | 45.575ms | 33.961ms |
| p99 | 48.466ms | 35.903ms |
| 최대 | 51.020ms | 36.581ms |
| 1초 초과 | 0건 | 0건 |
| 정상 입찰 DB 동기화 구간 | 3회 | 2회 |

분위수는 nearest-rank다. 동기화 수는 psycopg pipeline·별도 명령·commit/rollback 경계를 계측했으며 패킷 캡처가 아니다. 서버 실행 순서는 그대로 두고 쓰기 결과 대기와 별도 COMMIT 대기를 합쳤다. 전후 측정 시점의 네트워크·DB 부하 차이는 남는 변수다.

**이 수치는 브라우저 클릭→접수 확정 표시 또는 다른 참가자 화면 반영 지연이 아니다.** Streamlit Cloud에서 평균 60명·최대 80명 접속, 실제 브라우저 렌더링, 느린 네트워크를 포함한 200/300ms 목표와 p99 500ms 목표는 이번 측정으로 판정하지 않았다. 이전 SQLite 80개 브라우저 측정과도 직접 비교하지 않는다.

## 동시 입찰과 정확성

실제 DB의 마감 3초 전 4팀이 같은 금액을 동시에 전송했다. 전후 모두 1건만 신규 승인되고 나머지 3건은 현재 최고가보다 높지 않아 거절됐다. 전체 4건의 완료 시간(승인과 예상 거절 포함)은 다음과 같다. 표본이 4건이므로 성능 용량 판정용 p95/p99로 해석하지 않는다.

| 마감 직전 4팀 경쟁 | 변경 전 | 변경 후 |
|---|---:|---:|
| 평균 | 66.796ms | 58.612ms |
| p95 / p99 / 최대 | 87.649ms | 79.191ms |
| 1초 초과 / 예상 외 실패 | 0 / 0 | 0 / 0 |

전후 각각 12개 검사 단계, 17개 조건의 137개 계측 표본을 보존했다. 예상 거절·오류 주입·UUID 확인을 정상 승인 표본에 섞지 않았으며, 조건별 전체 분모와 결과별 분포는 원자료에 있다.

- **네 저장 위치와 COMMIT 오류:** 최고가·마감 수정, 입찰 원장 삽입, 세션 수정, BID 이벤트 삽입 각각에 DB trigger 오류를 주입했다. 별도 deferred trigger로 COMMIT 시점 오류도 주입했다. 원장·최고가·마감·변경 버전·선수 가격·팀 예산이 이전 상태를 유지하고 해당 UUID 조회가 비어 있음을 확인했다.
- **응답 유실:** 실제 COMMIT 완료 뒤 결과 전달 경계에서 예외를 주입했다. 새 연결로 같은 UUID를 조회하고 재시도해 원래 ID를 반환하며 입찰·이벤트·마감 연장이 추가되지 않음을 확인했다. 실제 통신 단절을 발생시킨 검증은 아니다.
- **UUID 동시 재전송:** 같은 계정·같은 UUID 4건에서 신규 승인 1건과 원래 결과 재사용 3건을 확인했다. 금액이나 계정을 바꾼 UUID 재사용은 거절했다.
- **5초 연장:** 정확히 5초 추가 및 선택한 5/10/30초의 최대 남은 시간 상한을 확인했다.
- **마감 서버 재확인:** 이전 마감 시각이 지났지만 연장된 마감은 지나지 않은 시점에, 오래된 후보 정보를 받은 실제 worker가 DB를 다시 확인했다. 조기 낙찰·선수 배정·예산 차감이 없었다.
- **클라이언트 복구:** 로컬 HTTP·컴포넌트 테스트로 미확정 UUID 우선 확인, 재로그인 시 계정 분리, 오래된 응답으로 상태가 되돌아가지 않는 동작을 확인했다. 이번 변경으로 실제 60/80개 브라우저의 재접속을 다시 실행하지는 않았다.

행 원문은 개인정보 최소화를 위해 저장하지 않았다. DB 상태 불변은 고정된 실행기의 런타임 비교와 해시 증거이며, 보고서에서 행 전체를 재구축할 수는 없다.

## 구현과 로컬 검사

- `roly/postgres.py`: 공통 `execute_batch()`는 기존처럼 커밋하지 않는다. 입찰 전용 `commit_bid_batch()`만 마지막 DML들과 `COMMIT`을 묶는다. 동기화 종료, COMMIT 성공 태그, 연결과 트랜잭션 상태를 확인한 후 ID를 반환한다.
- COMMIT 제출을 시도한 이후 결과 해석 오류까지 포함해 불확실한 결과는 `pending`으로 처리한다. 해당 연결을 폐기하고 기존 writer lock 아래에서 같은 UUID의 원장을 확인한다.
- `roly/live_auction.py`: receipt를 커밋 전에 준비하고, 이미 확정된 입찰을 외부 context가 다시 커밋하지 않도록 했다. 인증·예산·잠금·DB 시각·5초 규칙은 유지했다.
- `roly/auction_metrics.py`: 통합 구간 `bid_commit_pipeline`을 별도 계측한다.

로컬 관련 검사 **221개 통과**: 최종 핵심 90개(25.078초, 중복·실패·오류·skip 없음), 추가 도메인/HTTP/상태/알림 123개, 접수 복구 8개(51.840초). 추가 회귀의 최초 명령에는 기존 테스트의 import 경로 때문에 두 모듈 로딩 오류가 있었다. `tests` 경로를 추가한 뒤 해당 두 모듈의 8개 검사가 모두 통과했다. 이는 전체 저장소 회귀 790개를 이번 변경에서 재실행했다는 뜻은 아니다.

신규 검사에는 COMMIT 응답을 기다리기 전 ACK 반환 금지, 성공 태그가 있어도 닫힌/미종료 연결이면 pending, 커밋 후 결과 읽기 오류, 실제 psycopg 연결풀의 연결 폐기·교체·중복 반환 방지가 포함된다.
