# 롤리몰리 확정 기능·개발 구현 보고서

최종 갱신일: 2026-09-10

**현재 수정본:** 입찰 POST·UUID·DB 마감 판정을 유지하면서 경매별 공유 상태, 커밋 버전, WebSocket 전달과 재접속 복구를 추가했습니다. 전체 회귀 **790개·542.358초**, 실제 격리 PostgreSQL의 v7→v8 추가 마이그레이션·정합성 검증, 80명 TCP 전후 비교와 브라우저 정상·마감 직전·느린 통신망·재접속 비교를 완료했습니다. **지연은 줄었지만 200/300/500ms 목표 전체 통과는 아닙니다.** 한 PC의 80문서 정상 입찰 DOM p95는 확정 1,183.3→616.8ms, 다른 화면 1,854.7→362.4ms였습니다. 별도 브라우저 8개+TCP 72명 조건의 DOM은 목표 안에 들었지만 가시성 확인 rAF에는 긴 지연이 남았습니다. [최신 측정과 판정 기준](AUCTION_LATENCY_VERIFICATION.md)을 우선 참고하세요. 이번 수정본의 외부 배포·서버 지역 이전은 실행하지 않았습니다.

사용자의 최종 조건은 평소 60명 이하, 최대 80명입니다. 이번 최대 80명 결과를 60명 성능으로 환산하지 않았습니다. [무료 운영·직접 RPC 대안 검토](AUCTION_HOSTING_REVIEW.md)는 첨부 제안을 공식 문서와 현재 코드에 대조한 자료이며, 해당 후보의 신규 구현·배포·부하 검증 결과는 아닙니다. [최종 소스 ZIP](../dist/rolymoly-source.zip)과 [측정 원본·검산기 묶음](../dist/rolymoly-validation-20260910.zip)을 함께 제공합니다.

아래 배포 수치와 기존 기능별 설명은 수정 전 배포 이력입니다. 그 후 확보된 기존 Cloud 30초 관측은 다섯 문서·32개 종결 입찰이며 승인 ACK p95 1,370.5ms, 전체 ACK p95 3,648.7ms였습니다. 이 자료는 80명 성능 검증이 아닙니다. [기존 Cloud 기록 재분석](../test-artifacts/performance-20260910/cloud-30s-summary.md)

**직전 배포 후 확인 기록:** `8b7c148`을 main·rolymoly-test에 배포하고 Cloud 재시작 및 실제 브라우저 입찰을 확인했습니다. 라운지의 일반 내전·경매 내전 개설 섹션을 복구했으며 **일반 내전 보러가기·경매 내전 보러가기**로 문구를 통일했습니다. 열린 내전은 내전 목록에서, 기록은 최근 경기에서 확인합니다. README는 소개·실행·설정 위주로 축약했습니다.

경매 HTTP 오류는 Cloud 경유 시 인증 헤더가 전달되지 않아 앱의 401 응답이 외부에서 500으로 보이는 상황이었습니다. HTTPS POST 본문에 앱 세션·서버 확인값을 포함하도록 수정했습니다. 기존 출처 검사·취소 가능한 세션·서버 확인값 검증을 유지하고 인증값은 응답·명령 기록에서 제거합니다. 실제 브라우저 **10P 접수 안내·오른쪽 입찰 기록·DB 1건 접수·10P 낙찰**을 확인했습니다. 임시 경매 10번 59행을 정리했고 회원 22명·계정 23개·Riot 프로필 20개·랭크 40행을 보존했습니다.

## 1. 확정된 서비스 범위

롤리몰리는 클랜 회원의 개인 계정, 회원 정보, 일반내전, 실시간 경매, 경기 결과, 전력점수와 우승 업적을 함께 관리하는 웹앱입니다.

- 운영 자료는 **Supabase PostgreSQL 한 저장소**를 기준으로 합니다. 구글시트 연동·동기화·기존 자료 자동 가져오기는 사용하지 않습니다.
- 모든 회원이 개인 계정으로 가입하고, 운영진 승인 후 같은 계정을 계속 사용합니다. 매 경매의 팀장은 해당 경매에서 지정하며 팀장용 계정을 새로 만들지 않습니다.
- 승인 회원도 일반내전과 경매를 개설하고 본인이 만든 행사를 진행할 수 있습니다. 다른 사람이 만든 행사의 관리 권한은 자동으로 받지 않습니다.
- 경매는 웹에서 실시간으로 입찰합니다. 선수 순서는 무작위이며, 잘못된 낙찰 정정과 경매 초기화를 지원합니다.
- 클랜 티어·주 포지션·부 포지션·전력점수는 Riot API의 자동 평가값이 아닙니다. 운영자가 관리하는 정보와 API로 조회한 랭크 정보를 구분합니다.
- 일반내전 점수와 경매 우승 업적을 분리합니다. Riot 갱신이나 경매 낙찰 가격이 회원 전력점수를 자동으로 바꾸지 않습니다.
- 참가 명단은 사용자가 확정한 **카카오톡 명단 접수** 방식으로 받습니다. 앱에는 외부 모임 일정·출석 시스템을 새로 만들지 않았습니다. 멸망전도 이번 범위에서 제외합니다.

회원 목록과 라운지의 회원 선택은 같은 개인 프로필로 연결합니다. 본인 프로필의 닉네임 변경과 관리자의 회원 수정은 서로 다른 권한으로 처리합니다. 프로필의 일반내전·미배정 낙찰 금액은 `—`, 실제 낙찰은 `10 P`와 같이 표시하여 미입력을 0포인트와 구분합니다.

라운지는 같은 디자인의 **일반 내전·경매 내전 개설 섹션**을 각각 제공합니다. 각 섹션의 만들기 버튼은 기존 팀 편성 화면·경매 생성 팝업으로 연결합니다. 승인 회원 권한과 기존 로그인·DB를 유지하며 이동만으로 행사를 생성하지 않습니다.

**내전 목록**의 일반 내전·경매 내전 탭은 열린 내전을 모두 표시합니다. 비어 있으면 “진행 중인 일반 내전이 없습니다.”·“진행 중인 경매 내전이 없습니다.”를 표시합니다. 하단 버튼은 **일반 내전 보러가기·경매 내전 보러가기**로 같은 디자인을 사용하고, 진행 중인 내전으로 이동합니다. 종료·취소 행사는 열린 목록에서 제외하며 기록은 **최근 경기 → 전체 기록**에서 확인합니다. 이번 수정은 기존 동선 테스트 3개·17.187초로 확인했으며 실제 설정·Riot·PostgreSQL 접근은 없었습니다. [라운지 후속 검증](../test-artifacts/lounge-restore-focused.json)

준비 단계의 참가 팀 카드는 데스크톱에서 2열을 유지합니다. 사진·이름·Riot ID 아래에 티어, 주·부 포지션, 숙련도 아이콘을 왼쪽 정렬하고, 빈자리 안내 상자와 별도의 하단 5포지션 행은 제거했습니다. 긴 Riot ID의 한 줄 표시와 전체 ID 툴팁을 지원합니다. 실시간 경매는 팀 현황·경매와 입찰·입찰 기록의 3단 구성을 사용합니다. 실제 기기별 최종 표시·응답성 판정은 10절의 검수 범위와 구분합니다.

## 3. 계정·회원·권한

### 가입과 승인

1. 배포자가 비공개 경로에서 최초 관리자를 준비합니다. Supabase 공개 방문 화면에는 최초 관리자 생성 폼이 없습니다.
2. 회원은 로그인 아이디·비밀번호·비밀번호 확인·Riot ID·주 포지션·부 포지션으로 가입합니다. **최신 가입 화면에서는 현재 티어·현재 LP·신청 메시지 입력을 제거했습니다.**
3. 서버는 계정, 회원 `PENDING`, 가입 요청을 한 트랜잭션에 저장합니다. 같은 가입 요청 UUID의 재전송은 같은 결과를 반환하며 다른 내용으로 키를 재사용할 수 없습니다.
4. 승인 전에도 같은 계정으로 대기·보완 상태를 확인할 수 있지만 행사 개설·입찰·운영 작업은 허용되지 않습니다.
5. 관리자가 최신 신청 내용을 검토하고 승인합니다. 열린 승인 화면 이후 신청이 바뀌면 저장을 거부하고 최신 정보를 다시 확인하게 합니다.
6. 거절된 신청은 같은 계정으로 보완·재신청합니다. 승인된 회원은 이후 재가입하지 않습니다.

주·부 포지션은 가입 당시 선호 정보로 입력하며, 승인된 회원의 회원 원본 수정은 관리자가 담당합니다. 자기 닉네임 변경 권한이 포지션·클랜 티어·점수 수정 권한까지 확장되지는 않습니다.

권한 검사는 화면의 버튼 노출뿐 아니라 서버의 저장 메서드에서도 수행합니다. 승인된 개인계정에 진행자·관리자 역할을 부여할 수 있고, 그 계정과 회원 ID의 연결은 유지합니다. 마지막 활성 관리자를 해제하거나 탈퇴 처리하는 작업은 차단합니다.

관리자 화면의 일반회원 계정 별도 발급·재연결 동선은 제거했습니다. 호환용 API가 남아 있더라도 직접 가입한 개인계정의 회원 연결은 변경할 수 없습니다. 기존 방식의 계정을 재연결하는 API에도 진행 중 행사 검사, 표시 이름 동기화, 세션·복구 코드 폐기를 적용했습니다.

### 탈퇴·복귀·정보 변경

- 최초 승인과 탈퇴 회원 복귀는 별도 명령입니다. 과거 승인 회원은 승인 상태로 복귀하고, 승인되지 않은 거절 신청자는 `PENDING` 회원과 `REJECTED` 신청 상태로 돌아가 본인 로그인·보완이 가능합니다.
- 탈퇴 전 관리자 화면에서 참여 중인 내전과 팀장 여부를 확인합니다. 회원 탈퇴가 기존 경기·낙찰 기록을 삭제하지는 않습니다. 진행 중 행사를 어떻게 이어갈지는 운영자가 판단해야 합니다.
- 회원 변경·승인·거절·탈퇴·복귀에는 최신 버전 검사를 적용합니다. 같은 시각의 연속 변경에도 버전이 증가하여 탈퇴 후 복귀한 오래된 폼이 최신 값을 덮어쓰지 않게 합니다.
- `application_notes`는 기존 신청자 메시지, `notes`는 내부 운영 메모로 분리 보존합니다. 최신 가입 UI에서 메시지 입력을 없앴어도 과거 자료를 삭제하거나 내부 메모를 회원에게 복사하지 않습니다.

가입 항목 제거에 따른 연결도 점검했습니다. 현재 티어·LP·메시지는 필수 승인 조건이 아니며, 빈 기본값으로 가입·승인·명단 확정이 가능합니다. 조회 전 현재 랭크를 임의로 만들지 않습니다. 실제 문제로 확인한 것은 비어 있는 기존 신청 항목을 계속 보여주거나 미조회 상태를 수기 입력으로 설명하던 화면 문구였습니다. 관리자 화면·회원 편집에서는 값이 있는 과거 메시지만 **이전 신청 메시지**로 표시하고, 프로필의 실제 미조회 상태는 **아직 Riot 조회 정보가 없습니다.**로 구분했습니다. 과거 수기 자료와 내부 운영 메모는 보존합니다. 가입 항목을 없앤 것 자체가 DB 필수값 오류나 경매 지연의 원인이라는 증거는 없었습니다.

**화면 입력칸 삭제와 DB 컬럼 삭제는 구분합니다.** 이번에는 입력칸을 없앴고, `members`의 이전 티어·LP·출처·시각 컬럼과 `application_notes`를 물리적으로 DROP하지 않았습니다. 이전 티어 4컬럼은 v7 이관용 잔존 자료이며 최신 회원 조회는 `member_ranks`에서 값을 투영합니다. 반면 신청 메시지는 기존 가입·재신청 API 및 관리자 과거 메시지 표시에서 아직 참조하므로 DB에서만 삭제하면 가입이 깨집니다. 정규화 랭크 원본, 관리자 내부 메모 `notes`, 당시 경기 스냅샷도 이 가입 입력칸과 별개입니다. 후속 테스트 진행 기록 초기화는 이 회원 컬럼을 삭제하는 작업이 아닙니다.

### 비밀번호와 세션

현재 비밀번호 길이는 **10~256자**이며 특수문자·대문자·소문자·숫자의 조합을 강제하지 않습니다. 조합 규칙 변경은 검토 요청에 해당하며 새 정책으로 적용하지 않았습니다. 비밀번호는 salt를 포함한 PBKDF2 해시로 보관하며 원문을 저장하지 않습니다. 비밀번호 검증·생성의 느린 연산을 광범위한 DB 쓰기 잠금 밖에서 수행하고, 실제 저장 직전에 상태와 해시를 다시 확인합니다. 로그인 실패 제한도 적용합니다.

세션은 서버에서 유효성·만료·계정 활성 상태·회원 상태를 재검증합니다. 같은 탭 새로고침은 `sessionStorage`의 토큰을 재검증해 복원하며, 비밀번호를 브라우저에 보관하는 “브라우저 종료 후 자동 로그인” 기능은 아닙니다. 본인 비밀번호 변경과 관리자 발급 일회용 복구 코드는 기존 세션·기존 코드를 폐기합니다. 복구 코드는 해시·만료·한 번 사용 조건으로 관리하고 자동 메일·Discord 발송은 구현하지 않았습니다.

분실 시에는 **카카오톡으로 본인 확인 → 관리자에게 30분 유효·1회용 코드 발급 요청 → 기존 재설정 화면에서 새 비밀번호 저장** 순서로 운영합니다. 코드 발급·재설정은 기존 세션과 복구 코드를 폐기하여 이전 인증 수단의 재사용을 막습니다. 카카오톡 본인 확인은 운영자의 확인 절차이며 앱의 자동 인증 기능은 아닙니다. 로그인 아래의 별도 아이디·비밀번호 찾기 페이지는 아직 구현하지 않았습니다.

### 이번 v7 정규화

종전에는 솔로랭크 호환값을 `members.current_tier` 등에, 솔로·자유랭크 전체 응답을 `riot_profiles` JSON에 보관했습니다. 이번 변경은 두 랭크를 `member_ranks(member_id, queue_type)`의 고유 행으로 분리합니다. API JSON에서 랭크를 다시 원본으로 읽지 않고 정규화된 행을 조회하며, 기존 `current_tier` 조회 인터페이스는 **솔로랭크**를 반환하는 호환 표현으로 유지합니다.

두 행은 현재 회원의 Riot ID와 일치할 때만 연결합니다. 하나의 League API 응답에서 두 큐를 읽으므로 자유랭크 표시 때문에 Riot HTTP 요청을 추가하지 않습니다. 빈 응답으로 확인한 언랭크와 아직 조회하지 못한 자유랭크를 구분하며 승패·PUUID·조회 시각을 추측해 만들지 않습니다.

스키마 변경은 기존 계정·회원·점수·명단·세션을 유지하는 추가 마이그레이션입니다. 유효한 기존 캐시를 한 번 옮기고, 이후 재초기화가 새 랭크를 과거 값으로 덮어쓰지 않습니다. 손상·유실 캐시가 있는 기존 회원의 마지막 정상 솔로랭크는 API 출처를 유지하여 보존하되, 모르는 승패·PUUID·자유랭크·조회 시각을 만들지 않습니다. 별도 임시 PostgreSQL의 실제 v6→v7 업그레이드 **7단계가 8.969초에 통과**했습니다. 10회원·2계정·일반경기 1건의 로그인·점수·스냅샷, 수기 및 API 랭크 5행, 재초기화·오래된 Riot ID 저장 거절·닉변 무효화를 확인하고 QA 스키마를 삭제했습니다. [v6→v7 검증 결과](../test-artifacts/member-ranks-v6-v7-postgres.json)

그 후 공유 검수 DB에도 **v7을 실제 적용·커밋했습니다**. 적용 전 백업 체크섬·복원 결과·대상 프로젝트를 확인하고, 커밋 전에 기존 자료 보존을 대조했습니다. 회원 **22명**, 계정 **23개**, 공개 Riot 프로필 **20개**, 당시 행사 **1개·4팀·참가자 20명**을 유지하면서 `member_ranks` **40행**을 만들었습니다. 계정·세션·점수·역사 기록과 관련 33개 기존 테이블을 보존했고, 회원 표시·공개 프로필·프로필 메타데이터·조회 시각의 전후 의미 해시가 일치했습니다. 적용은 **4.703초**, Riot HTTP 요청 0건입니다. DB 적용과 별도로 이후 Cloud 배포·실제 경쟁은 8절에서, 테스트 행사 삭제는 9절에서 완료 결과를 확인합니다. [공유 DB 적용 결과](../test-artifacts/shared-rank-v7-applied.json)

### 본인 닉네임 변경

승인 회원은 본인 프로필 또는 내 계정의 “닉네임 변경”에서 전체 `닉네임#태그`를 수정합니다. 서버는 본인 세션·회원·현재 버전을 다시 확인하며 중복 Riot ID와 오래된 폼을 거절합니다. 로그인 아이디·계정 ID·회원 ID·로그인 유지·주부 포지션·클랜 티어·점수·업적·과거 명단과 경기 기록은 보존합니다.

실제 Riot ID가 바뀌면 이전 조회 결과와 진행 중 작업을 폐기합니다. A→B→A로 바뀌어도 첫 A의 오래된 진행 작업이 새 프로필에 적용되지 않도록 보호합니다. 대소문자 등 동일한 정규화 ID의 표기 변경은 구분합니다. 닉네임 저장 자체가 Riot API를 자동 호출하지는 않습니다.

### Riot 요청·실패·재시작

- 공개 페이지는 저장된 프로필만 조회합니다. 회원의 “갱신하기” 등 명시적인 요청이 작업을 예약하고, API HTTP는 별도 Python 작업자가 실행합니다.
- 조회 작업은 회원 ID·현재 Riot ID·단계·임대 기간을 DB에 저장합니다. 한 단계씩 진행하여 한도 대기·프로세스 재시작이 처음부터의 반복 호출을 만들지 않게 합니다.
- 같은 API 키의 1초 20회·120초 100회 요청 한도와 대기 상태를 DB에서 공유합니다. 허용된 로컬 체험도 운영과 같은 요청 예산을 사용하고 회원 캐시·작업 자료는 분리합니다.
- 429의 `Retry-After`를 존중하고, 401/403은 키 교체 또는 명시적인 재시도 전까지 전체 재시도를 막습니다. 일시 실패·`not_found`가 마지막 정상 랭크·숙련도를 지우지 않습니다.
- HTTP 동안 경매 쓰기 잠금을 잡지 않습니다. Riot 작업·요청 한도의 잠금과 경매 쓰기 잠금도 구분합니다.
- Data Dragon 자료 실패 시 마지막 정상 챔피언 이름·이미지 메타데이터를 보존합니다. 캐시의 내부 PUUID·키 관련 값은 공개 프로필로 보내지 않습니다.
- 숙련도 4·5위가 없으면 빈 챔피언을 만들지 않으며, 숙련도 점수를 승률이나 KDA로 바꾸지 않습니다.

API 키의 실제 운영용 승인·만료·교체 담당과 장기 운영 한도 확인은 운영 준비 사항입니다. 정규화·PostgreSQL 성능 시험에서는 Riot HTTP를 호출하지 않았으며, 이후 사용자가 요청한 실제 API 장애 진단·갱신 검수는 아래와 같이 별도 진행했습니다.

## 5. 일반내전과 경기·점수

일반내전은 10명 또는 20명을 선택하여 팀을 편성합니다. 검색·선택과 카카오톡 명단 붙여넣기를 지원합니다. 번호 접두어를 제거하고 첫 `/` 앞 Riot ID를 추출한 뒤 DB의 정확한 승인 회원과 대조합니다. 미등록·중복·미승인·모호한 ID는 미리보기에서 확인하고 자동 추가하지 않습니다. 뒤에 붙은 티어·포지션 메모가 회원 원본을 덮어쓰지 않습니다.

포지션과 전력을 바탕으로 자동 밸런싱하거나 수동 배정할 수 있습니다. 첫 경기 전 명단 재편성과 서로 다른 팀의 같은 포지션 선수 교환을 지원합니다. 선수 교환은 팀장을 이동하지 않으며 화면의 최신 명단 버전·요청 UUID를 검사합니다. 같은 교환 재전송이 한 번 더 뒤집히지 않고, 다른 내용으로 UUID를 재사용하면 거절합니다. 경기 기록이 생긴 뒤 명단을 자유롭게 교체하는 기능은 아닙니다.

일반내전의 초기 점수 정책은 승리팀 각 **+10**, 패배팀 각 **−10**입니다. 운영진이 정책을 바꾸면 새로 만든 일반내전에 적용하고 이미 만든 내전은 생성 당시 정책을 유지합니다. 부전승에는 실제 경기 판수·경기 점수를 부여하지 않습니다. 전적·승률은 유효하게 확정된 일반내전 경기로 계산합니다.

결과 저장은 해당 행사·대진·참가 회원의 연결을 검사합니다. 같은 결과 요청 재전송과 중복 종료를 방어하며, 정정·무효 처리는 기존 원장을 보존하고 필요한 경기 증감만 다시 계산합니다. 별도로 입력한 수동 점수 보정이 경기 정정 때문에 삭제되지 않습니다. 수동 보정도 대상·금액·사유·관리자에 연결된 UUID 영수증으로 한 번만 반영합니다.

## 6. 실시간 경매·낙찰·복구

### 준비와 대진

경매는 4·6·8팀을 지원하며 최종 팀 구성은 팀당 5명입니다. 참가 명단 확정 시 당시 전력·티어·주부 포지션을 저장하고, 경매마다 팀장을 지정합니다. 팀장 전력을 반영한 기본 예산을 제공하며 주최자·관리자는 시작 전에 팀별 시작 포인트와 선수별 시간을 조정할 수 있습니다. 시작 후 포인트를 임의로 다시 바꾸지는 않습니다.

최초 선수 순서는 한 번 무작위로 구성하며 설정 저장만으로 다시 섞지 않습니다. 4팀은 풀리그·토너먼트·순위 결정전, 6·8팀은 풀리그·토너먼트·조별리그와 결승을 지원합니다. 4팀 순위 결정전은 결승과 3·4위전을 포함합니다. 대진 확정에는 팀 정원과 포지션 구성이 필요합니다.

### 입찰과 시간

- 해당 경매의 팀장과 연결된 개인계정만 자기 팀으로 입찰합니다. 서버에서 계정 상태·팀·선수·정원·포인트·최고가·마감 시각을 재검증합니다.
- 입찰 시간은 **5/10/15/20/25/30초**, 기본 10초입니다. 유효한 새 입찰의 마감은 `min(기존 마감 + 5초, DB 현재 시각 + 선택 시간)`입니다. 선택한 시간이 연장 후 상한이며 고정 10초 상한이 아닙니다.
- 같은 금액은 서버에서 먼저 유효하게 확정된 입찰 한 건이 인정됩니다. 브라우저 클릭 시각으로 순서를 결정하지 않습니다.
- 중복 UUID 재전송은 원래 영수증을 반환합니다. 같은 UUID로 계정·선수·금액을 바꾸면 거절하고 중복 연장·차감을 하지 않습니다.
- 마감 판단에는 쓰기 잠금을 얻은 뒤의 PostgreSQL DB 시각을 사용합니다. 마감 전에 요청했더라도 잠금 대기 후 이미 마감됐다면 거절합니다.
- 낙찰 시 팀 배정과 포인트 차감을 함께 반영합니다. 초기 0포인트 입찰과 실제 미입력을 구분합니다. 낙찰·유찰 후 다음 선수 준비 시간은 최소 3초입니다.
- 주최자·관리자는 일시정지·재개할 수 있고 일시정지의 남은 시간을 보존합니다. 일시정지·준비·정원 완료 상태에서는 입찰을 받지 않습니다.
- “유찰 재시작”은 현재 라운드 전체가 끝난 뒤 유찰 선수만 다시 섞어 진행하며 3초 준비 시간을 둡니다. 아직 남은 순서가 있으면 사용할 수 없습니다.

### 잘못된 낙찰과 경매 초기화

관리자 낙찰 정정은 일시정지 중 또는 경기·대진을 만들기 전의 허용된 완료 단계에서 사용합니다. 대상 선수·팀·금액과 환급·재배정 내용을 먼저 보고 확인하며 최신 상태 지문과 UUID를 검사합니다. 낙찰 취소는 기존 기록을 보존하고 해당 선수의 새 경매 차례를 만듭니다. 경기 결과가 생긴 뒤 임의로 과거 낙찰을 바꾸는 기능은 아닙니다.

경매 초기화는 주최자·관리자가 미리보기와 확인을 거쳐 실행합니다. 허용된 경기 시작 전 단계에서 팀장·참가 명단·원래 예산·시간을 보존하고 판매·차감을 되돌린 뒤 `READY`와 새 무작위 대기열을 만듭니다. 과거 입찰·차례·감사는 삭제하지 않으며 같은 UUID를 다시 보내도 재초기화하지 않습니다. 입찰이나 다른 창의 변경으로 미리보기 상태가 달라졌다면 다시 확인해야 합니다.

### 경기 결과·우승 보상·중단

경매 대회의 경기 결과는 회원 전력점수를 바꾸지 않습니다. 정상 종료 시 실제 우승팀 5명에게 4팀은 고양이 1개, 6팀은 별 1개, 8팀은 메달 1개를 각각 지급합니다. 고양이 5개는 별 1개, 별 5개는 메달 1개, 메달 5개는 트로피 1개로 환산하고 같은 경매의 중복 지급을 막습니다.

관리자는 종료·우승 보상 전의 허용된 경매 결과를 정정할 수 있습니다. 후속 경기 무효화와 새 대진을 미리 보고 확인하며, 원경기·정정 이력·후속 무효 기록을 보존합니다. 풀리그 동률 추가 경기, 토너먼트 결승·3위전, 조별리그 결승의 의존 관계를 함께 계산합니다. 이미 우승 보상을 지급한 경매를 무제한 재개·정정하는 기능은 아닙니다.

실제 경기를 진행한 뒤 중단해야 하면 관리자가 사유와 함께 기록을 보존하고 중단 종료할 수 있습니다. 이미 확정된 일반내전 점수와 경매 낙찰 내역을 지우지 않으며 남은 경기만 중단하고 경매 우승 보상은 지급하지 않습니다.

기본점수 이력, 경기 점수 원장, 수동 보정, 업적은 서로 분리하며 회원 ID와 행사·경기 ID로 연결합니다. 화면에서 계산한 숫자를 별도의 운영 원본으로 저장하지 않습니다. 현재 프로필과 과거 경기 스냅샷의 값이 다른 것은 의도된 기록 보존입니다.

PostgreSQL 앱 스키마는 공개 API 역할 `anon`·`authenticated`가 직접 읽거나 변경하지 못하도록 권한을 회수합니다. SQL 값은 매개변수로 전달하고, 오류 화면에 접속 문자열·SQL 내부 값·키를 노출하지 않습니다.

Supabase에서 앱 테이블을 확인할 때는 연결된 프로젝트의 Table Editor에서 기본 **public** 대신 **rolymoly** 스키마를 선택합니다. `members`는 회원, `accounts`는 로그인 계정, `member_ranks`는 솔로·자유랭크, `riot_profiles`는 아이콘·숙련도 등의 조회 자료입니다. `canonical_id`는 Riot ID의 앞뒤 공백을 정리하고 대소문자를 통일한 중복 검사 키입니다. 예를 들어 `겨울#KR99`와 `겨울#kr99`를 같은 ID로 판단합니다. 닉네임이 바뀌면 이 값도 바뀔 수 있으며, 과거 기록을 이어 주는 고정 식별자는 별도의 회원 `id`입니다.

쓰기 작업은 필요한 검증·변경·원장·감사·영수증을 같은 트랜잭션에 넣고 충돌을 직렬화합니다. 경매 조회는 `READ ONLY REPEATABLE READ`로 인증과 화면 데이터를 같은 스냅샷에서 읽습니다. 연결풀 반환 시 rollback·세션 초기화를 유지하여 다른 조회가 이전 스키마·트랜잭션 상태를 물려받지 않게 합니다. 전역 로그인 권한이나 경매 상태를 오래 캐시하는 방식으로 속도를 높이지 않습니다.

직전 두 Cloud 실행의 18명령을 최초 UUID 확정 응답으로 분해했습니다. 입찰 callback은 실행별 전체 RTT 합의 **52~63%**, view 조회는 약 **11%**, 아직 세분하지 못한 전달·대기 구간은 **24~35%**였습니다. 18건은 모두 전송 1회였으므로 재전송이 이 지연의 원인으로 관측되지는 않았습니다. 낙찰·유찰 전환의 875관측은 같은 응답을 반복한 자료이며 세션별 345개 응답 계측으로 구분했습니다. 이를 독립 표본으로 합쳐 p95나 향상률을 계산하지 않았습니다. [저장 자료의 구간별 분석](../test-artifacts/auction-responsiveness/SAVED_CLOUD_RESPONSIVENESS_ANALYSIS.md)

새 경로는 앱과 같은 출처의 HTTP로 입찰 명령을 보내며, 접수 응답이 전체 관전 스냅샷을 기다리지 않도록 분리했습니다. 입찰 확인 중에도 별도의 단일 조회를 이어가고 같은 로그인·경매 문맥의 팀 카드·입찰 기록·선수 순서에 최신 값을 전달합니다. 로컬 금액 조작은 서버 요청을 만들지 않습니다. 실제 API 경로가 활성화된 경우 예전 CCv2 입찰 쓰기를 막아 서로 다른 접수 기록 관리 경로가 섞이지 않게 했습니다.

기존 로그인 토큰·최신 권한·서버 마감·UUID·포인트의 원자적 저장은 유지합니다. 서버 실행 세대를 확인하고, 재접속 때 저장된 UUID는 접수 확인만 수행하여 새 입찰로 바꾸지 않습니다. 바깥 응답과 내부 스냅샷의 문맥·요청 echo·경매 번호, ACK의 UUID·선수·금액을 검사합니다. ACK는 화면 스냅샷이나 시계의 최신성을 갱신하지 않으며, 종료된 화면에 늦게 온 HTTP 응답이 타이머·이벤트 수신기를 다시 설치하지 않도록 수명주기를 분리했습니다. 접수 불명확 응답은 1.2초 뒤 확인하고, 최초 timeout은 기존 3~5초 범위를 유지합니다.

### 이전 추가 개선 `033b27b`: 배포·실제 검수 이력

독립 화면 조회의 트랜잭션 시작·조회·종료를 한 pipeline에 묶어 동기화 왕복을 **3→1회**로 줄였습니다. 정상 신규 입찰은 선수 최고가·접수 기록·세션·진행 기록의 4개 저장을 함께 전송해 **8→5회**로 줄였습니다. 기존 서버 권한·DB 마감·최고가·정원·포인트 검증과 최종 commit은 유지합니다. 저장 중 한 문장에 실패하면 전체 입찰이 rollback되며, 외부에서 시작한 트랜잭션을 독립 조회가 임의로 종료하지 않습니다.

일반 조회는 응답 뒤 350ms를 더 기다리던 방식에서 **직전 요청 시작 기준 500ms 간격**으로 바꿨습니다. 일반 조회는 한 번에 하나만 전송합니다. 입찰의 첫 재시도 대기는 최소 3초이며, 재전송 없이 확정된 이전 입찰의 시간을 참고해 최초 제한을 최대 5초까지 조정합니다. 이후에는 최대 10초까지 대기를 늘리며 같은 UUID를 재전송합니다. 서버가 접수 여부 확인 중이라고 응답하면 기존 1.2초 확인 간격을 유지합니다.

독립 검토에서 두 경계 결함을 재현하고 수정했습니다. 새 입찰이 직전 조회 timeout의 긴 대기를 물려받던 문제, 오래된 화면 응답이 연결 상태·시계를 최신으로 갱신하던 문제입니다. 정확히 같은 UUID·선수·금액의 늦은 확정 응답은 처리하면서 오래된 화면 상태는 버립니다.

브라우저 내부에 최초 입찰 전송부터 정확한 확정 응답까지의 경과시간과 전송 횟수, 입찰·선수의 최초 DOM 반영 시각을 기록합니다. 서버의 콜백 처리와 조회 시간도 구분합니다. 이 값은 진단용이며 화면 문구로 표시하거나 시간 보정에 중복 가산하지 않습니다. DOM 반영은 실제 픽셀 그리기 완료와 다르며, PC 절대 시각과 DB 절대 시각의 차이를 그대로 통신 지연으로 계산하지 않습니다.

## 9. 배포·워커·백업

현재 구성은 Python 3.11, Streamlit 1.63.0, pandas 2.3.3, psycopg 3.3.5, psycopg_pool 3.3.1입니다. `app.py`와 기존 Cloud 호환용 `streamlit_app.py`는 같은 앱을 실행합니다. 로컬 실행기는 `python -m roly.server`이며 앱과 마감 워커에 같은 저장소를 전달합니다.

| 배포 모드 | 저장소·체험 |
| --- | --- |
| `test` | 공용 Supabase 필수, 검수용 배지, 실제 가입·로그인, Workspace·체험 계정·seed 차단 |
| `production` | 공용 Supabase 필수, 체험 차단, 검수용 배지 없음 |
| `local` | 명시적인 개발·검증 및 격리 체험 SQLite 허용 |

모드 기본값은 production이며 잘못된 모드·누락되거나 잘못된 운영 DB 설정에서는 실행을 중단합니다. 명시적 개발용 데이터 디렉터리·대상 설정은 로컬 예외로 처리하되 test/production에서 SQLite로 조용히 대체하지 않습니다. 모드 이름만 바꿔서는 DB 프로젝트가 분리되지 않습니다. 검수와 정식 운영의 프로젝트·Secrets 선택은 배포자가 확인해야 합니다.

비밀값은 로컬 `.streamlit/secrets.toml` 또는 Cloud Secrets에서 별도로 설정합니다. 저장소·소스 ZIP에는 실제 Secrets, `.data`, DB 파일, 검수 비밀번호 파일, 원본 백업을 포함하지 않습니다. 검수·운영에서는 `[app] environment = "test"` 또는 `"production"`, `[riot] allow_demo = false`를 사용합니다.

경매 마감은 여전히 **Python 앱 워커 프로세스**에 의존합니다. 워커가 종료되거나 Cloud가 휴면 상태이면 그동안 즉시 정산하지 못하며, 다시 실행하면 DB에 남은 마감 시각·상태를 기준으로 처리합니다. 별도 PostgreSQL 검수에서 워커 종료 후 미정산, 재시작 후 낙찰 1회, 다음 선수 최소 3초, 일시정지 보존, 두 워커의 중복 정산 방지를 확인한 이력이 있습니다. **독립 DB 마감 워커·Cloud 휴면 상태의 지속 처리는 구현 완료가 아닙니다.**
